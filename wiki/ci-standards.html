    04 · CI / CD

    How every repo ships

    The venus-os-ci-toolkit provides shared workflows and release tooling. Each project defines its own validation commands and artifact requirements; follow its checked-in contribution and release guides.

    Reusable workflows and tools

    Workflow or toolPurpose
    python-ci.ymlruff lint · mypy · pytest · coverage gate → Codecov
    go-ci.ymlgolangci-lint · govulncheck · tests · coverage gate → Codecov
    tools/scorecard-scanValidates Scorecard results and writes SARIF; the calling workflow handles upload
    auto-approve-reusable.ymlMetadata-only approval for eligible pull requests under the configured author and reviewer policy

    Consuming a toolkit workflow — always pinned to a full commit SHA:

    jobs:
  test:
    uses: victron-venus/venus-os-ci-toolkit/.github/workflows/python-ci.yml@875762362bb31b4899bf02fdf9e835188dc5eb80

    Non-negotiable rules

    • Pin everything. Every uses: in every workflow resolves to a full commit SHA — never a tag or branch. Tags move; SHAs don't. This is the supply-chain boundary.
    • Harden runners. Workflows include step-security/harden-runner to audit egress network calls.
    • Never push to the default branch. Feature branch from the default branch, open a PR, let CI and CodeQL pass, merge via review. Eligible, non-draft PRs receive auto-approval independently of labels. The automerge label enables automatic merging after required checks and review requirements are satisfied.
    • Conventional Commits. feat:, fix:, docs:, chore: — release tooling parses them.
    • Approval and merge are separate. Follow the approval caller example and merge policy guide. Keep approval jobs metadata-only and preserve the documented eligibility checks.

    Releases

    Application repositories use their .release-policy.json, RELEASING.md and docs/release-workflow.md to define checks, artifacts and release channels. The release pipeline creates immutable beta and RC candidates. Stable promotion requires approval and copies the verified, tested RC bytes without rebuilding. A GitHub release does not deploy production; container registry publication and deployment are separate operations.

    Use the target repository's release commands. Do not create release tags by hand or restore the retired direct-tag publication workflow. Infrastructure and community repositories run validation and explicit deployment instead of application release channels. See the organization release overview.

    Version synchronization

    Review base-version changes through a pull request. The target repository's release policy declares which version files must agree; projects do not all use the same file names or package format. Release tooling allocates candidate versions, applies declared build-time version overlays and records the source revision and artifact checksums. Follow that repository's versioning guide rather than manually changing a version and pushing a tag.

    Why so strict? These repos control physical hardware. A moved tag or an unreviewed workflow edit is not a cosmetic risk — treat CI config with the same care as control code.
