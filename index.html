    01 · Install

    Installing on Venus OS

    Use the selected repository's released installer and configuration example. These projects are independent repositories; there is no organization-wide bootstrap.sh.

    Check the device first

    cat /opt/victronenergy/version
python3 --version
uname -m
command -v svc svstat multilog

    The September 2026 audit used Venus OS v3.75 and Python 3.12.13 on a Raspberry Pi 3 Model B with approximately 1 GB RAM. Other hardware and firmware need their own checks.

    Native service installation

    Use daemontools: persistent application and service files under /data, symlinks under volatile /service, and offline boot restoration from /data/rc.local before any exit 0. A systemd unit or an unreferenced /data/rc/S99* file will not install a native Venus service.

    Install SetupHelper when the package requires it. Preserve local configuration and venvs during updates. Check dependencies before stopping the existing service; do not run global pip upgrades or network installers at boot.

    • Battery and PV bridges: follow dbus-mqtt-battery, dbus-virtual-battery, and dbus-tasmota-pv.
    • Home Assistant bridges: Emporia and water tank, pump and valve depend on their configured HA endpoint.
    • dbus-ev reads Mercedes or Home Assistant vehicle telemetry; its integrated charger requires the Mercedes backend. The standalone charger repository is archived. Follow the migration and rollback guide and never run two owners of the same charger service.
    • inverter-control uses local_config.py, with a preserved copy under /data/setupOptions/inverter-control/. Verify metering before enabling control.
    • Observability: use metrics-only mode when trace export is unnecessary.

    Inverter Climate thermostat controls

    inverter-climate runs natively on Venus OS and uses the existing Home Assistant thermostat integration, including Google Nest. It reads local D-Bus energy data and publishes an Inverter Climate room-temperature device.

    In SetupHelper PackageManager, add package inverter-climate, GitHub user victron-venus, branch latest. This is the packaged stable release; main is development source. Python 3.12+, firmware D-Bus/GLib bindings and velib_python are required.

    A first installation stays disabled until configured and explicitly started. Follow the native lifecycle guide and configuration example. Keep HA credentials and configuration private under /data/setupOptions/inverter-climate; select the real thermostat and energy sources, and begin with [service] mode = "observe".

    Settings → Devices shows temperature and metadata. For manual commands, add control_enabled = true to the existing [device] section and restart the service according to the lifecycle guide. Open the Switch pane from the small icon at the upper left of GUI v2: Temperature setpoint is a slider, and Heating mode offers Heat / Off. The same controls are available through VRM Remote Console.

    Manual control can remain in observe mode. Automatic preheating requires the separate mode = "active" choice and a validated energy configuration. Updates preserve private settings, device identity and command journals; uncertain commands are not automatically retried. Follow the package guide for recovery.

    Keep companion workloads off the GX

    Run Docker dashboards, Grafana/Loki, databases and forecasting on a NAS/server. Flash ESPHome on the ESP32. Check architecture and resource headroom before adding optional dashboard binaries to a GX. Not every repository is a deployable native package.

    Verify uptime, logs and D-Bus types

    svstat /service/dbus-mqtt-chain1 /service/dbus-mqtt-chain2
svstat /service/dbus-ev /service/vrmlogger
tail -n 80 /var/log/dbus-ev/current
tail -n 80 /var/log/vrmlogger/current

    svc -s suspends a process; it does not show status. Never cat supervise/ok, which is a FIFO. Repository names and supervised instance names can differ.

    Verify numeric D-Bus values, /Connected, fresh source data and successful VRM uploads. Native MQTT topics use N/<portal-id>/...; raw sensor and application topics have their own contracts. Use the actual portal ID and the existing GX broker.

    On the audited device /var/log points to persistent /data/log. Bound logs with multilog and keep frequent cursors/heartbeats under /run. Test reboot and firmware recovery during a planned maintenance window.

    A connected broker or successful HTTP response does not prove fresh telemetry. Keep blocking requests outside the D-Bus main loop, preserve acquisition timestamps through queued callbacks, and expire MQTT fields independently. Freshness checks and network polling can have different intervals.

    The September audit closure records the additional releases, device checks, passive meter capture and remaining physical validation limits.

    Read the complete installation guide and service audit.

    02 · Architecture

    How the system fits together

    Venus OS models devices on its local D-Bus. Bridges and companion applications use MQTT, HTTP or WebSockets according to their own integration contracts. The repository map is not a live deployment inventory.

    The five layers

    1 · Hardware & sensing

    ESP32s, Tasmota plugs, CT clamps, Emporia Vue submeters, EV chargers and water tanks/pumps provide readings through firmware or configured Home Assistant entities. esphome-jbd-bms-mqttdbus-esphome-grid-sensordbus-evdbus-pump

    2 · D-Bus services

    Translators running on the GX: MQTT→D-Bus for the audited battery and Tasmota PV bridges, and Home Assistant→D-Bus for Emporia, EV, charger and pump measurements. Third-party hardware appears as Victron device services. dbus-mqtt-batterydbus-tasmota-pvdbus-emporia-vue

    3 · Control & policy

    inverter-control calculates setpoints and applies its configured validity, limit and watchdog policies before D-Bus writes. It consumes EV data published by the Home Assistant bridges. The archived venus-os-governance project does not gate this deployed path, and no dbus-event-log service was running on the audited GX. These repositories must not be treated as an installed authorization or audit layer. inverter-controlvenus-os-governancedbus-event-logdbus-ev

    4 · MQTT distribution

    State leaves the GX over MQTT topics. fastapi-mqtt-gateway adds REST/WebSocket access for clients that can't speak MQTT natively. fastapi-mqtt-gateway

    5 · Consumption

    Dashboards (Go binary on-GX, Python/Docker, Vue SPA, Tauri desktop), Home Assistant, observability stacks and optional forecasting tools. Verify each configured caller before assuming forecasts affect controller decisions. inverter-dashboard-gosolar-forecast-langgraphvenus-os-observabilityinverter-monitoring

    Thermostat integration

    inverter-climate spans the D-Bus and control layers. A native supervised service on Venus OS reads local system energy, publishes room temperature, and exchanges thermostat state and commands with Home Assistant. HA owns the existing Google Nest connection and authentication.

    The stock GUI v2 Switch pane and VRM Remote Console can show its optional temperature slider and Heat/Off selector through the Switchable Output API on the same temperature device. Observation is the default; manual controls and automatic preheating are enabled separately. HA requests run outside the D-Bus loop and the separate ESS controller.

    The native path needs no companion gateway or GUI patch, while Nest still relies on HA and its cloud integration. For a gas furnace, the configured heating-power estimate describes electrical demand; it does not measure heat or gas and is not published as another AC load. See the installation and control guide.

    Why two buses instead of one

    D-Bus is how Venus OS models batteries, PV inverters and grid meters as com.victronenergy.* services. The ESS controller reads and writes that local bus.

    Companion dashboards, Home Assistant, Grafana and forecasters use MQTT, HTTP or WebSockets according to their integration contracts. Thermostat commands from inverter-climate reach Home Assistant over its REST API, while the GX-facing temperature device and GUI controls use D-Bus. Validate freshness and command acknowledgements at each boundary.

    Control path vs telemetry path

    Control path (amber)Telemetry path (cyan)
    ProtocolD-Bus for ESS; HA REST for thermostatsMQTT / REST / WebSocket
    WritersConfigured controller and native Venus servicesPer-service publishers and gateways
    AuditVerify actual logging; event-log is an optional integrationConfigured metrics and logs
    TimingESS cadence and D-Bus latency; HA/cloud latency and observed confirmation for thermostatsSource-specific freshness limits
    Failure modeESS validity, hold and watchdog policy; thermostat availability and journaled uncertain outcomesMark unavailable inputs; stale telemetry can affect control

    Cross-cutting concerns

    • Forecasting: optional forecast consumers need a configured, tested control contract; repository availability alone does not close a control loop.
    • AI access: mcp-venus-os provides its own validation and write-confirmation rules. Verify its deployment and transport separately from the controller.
    • EV data path: dbus-ev publishes vehicle telemetry from Mercedes or Home Assistant and can own the Mercedes charger service. The standalone charger repository is archived. Follow the migration guide, retain a single charger owner, and preserve unavailable-value handling during source outages.
    • Testing: broker and simulated D-Bus integration tests complement installer checks and device observation. Firmware compatibility and cold-boot recovery need target-device validation.

    03 · Integration

    Writing for Venus OS

    Conventions shared by every service in this ecosystem. Follow them and validate service discovery, numeric path types, freshness and resource use against the target firmware.

    D-Bus service naming

    Venus OS discovers services by their bus name. The pattern:

    com.victronenergy.<type>.<suffix>

com.victronenergy.battery.jbd_mqtt        # dbus-mqtt-battery
com.victronenergy.pvinverter.tasmota      # dbus-tasmota-pv
com.victronenergy.grid.esphome_ct         # dbus-esphome-grid-sensor
com.victronenergy.acload.emporia_vue_1    # dbus-emporia-vue, one per channel
com.victronenergy.temperature.inverter_climate_<identity> # inverter-climate

    Pick <type> from what Venus OS already understands — battery, pvinverter, grid, acload, solarcharger, temperature. A wrong type means the GX ignores your service no matter how correct the paths are.

    Paths every service should publish

    PathMeaning
    /ProductId, /ProductNameIdentity shown in the device list
    /ConnectedSource availability; report 0 when required inputs are unavailable
    /Status or /ErrorCodeFault visibility without opening logs
    Type-specific valuese.g. /Dc/0/Voltage, /Ac/Power, /Soc

    Native thermostat controls

    inverter-climate publishes /Temperature in Celsius with /TemperatureType = 3 (room). Its identity suffix is a stable hash, and its optional /SwitchableOutput/0 temperature slider and /SwitchableOutput/1 Heat/Off selector belong to the same device. GUI v2 and VRM Remote Console use those standard controls without a GUI patch.

    Manual commands are opt-in, validated against fresh HA capabilities and journaled before dispatch. The D-Bus thread only queues requests; HA I/O runs outside it. Readback reflects HA observations, and uncertain commands are not replayed after restart. See the complete D-Bus contract and installation guide.

    MQTT contracts

    Native Venus telemetry uses N/<portal-id>/<service>/<instance>/<path>; read requests use R/<portal-id>/.... Raw ESPHome/Tasmota sensor topics and application inverter/state use separate schemas. Use the publisher's README and a real portal ID. Do not assume a universal victron/# namespace.

    Native installation contract

    /data/service-name/
  service/service-name/run
  service/service-name/log/run
  application files and local configuration
/service/service-name -> /data/service-name/service/service-name

    Recreate the link from /data/rc.local before any early exit. Use svc and svstat, preserve service directory inodes on updates, and install dependencies before stopping the service. Firmware replaces rootfs files; keep persistent state under /data. See the installation guide and the service template.

    D-Bus value contract

    Register all required paths before publishing the service name. Publish numeric values as numbers and unavailable measurements using the standard invalid value, not fabricated zero. Apply MQTT-thread updates on the GLib loop. Prefer batched ItemsChanged signals and bounded reconnection with backoff. A /BatteryCapacity string caused the stock VRM logger to crash in the September 2026 audit.

    Rules that keep the fleet debuggable

    • Log to stdout/stderr — multilog writes it to the configured bounded log directory; never background yourself.
    • Reconnect loops with backoff — MQTT and D-Bus drop during GX reboots; treat disconnects as normal.
    • One service, one job. Translation, decision-making, and audit live in separate processes (see Architecture).
    • Verify control integration. No governance or event-log service was running on the audited GX. Repository availability alone does not prove that live writes are mediated or audited. Inspect the deployed controller and validate each accepted D-Bus write.
    • Source availability matters. dbus-ev reads Mercedes or Home Assistant and publishes to D-Bus; its integrated charger requires the Mercedes backend. inverter-control consumes D-Bus values. Mark unavailable source data correctly during outages and consult the migration guide before replacing the archived standalone charger.
    • Daemontools logging. Services like dbus-tasmota-pv use the multilog daemontools pair for log rotation; others use stdout capture. Check each repo's service/run for the pattern.

    04 · CI / CD

    How every repo ships

    The venus-os-ci-toolkit provides shared workflows and release tooling. Each project defines its own validation commands and artifact requirements; follow its checked-in contribution and release guides.

    Reusable workflows and tools

    Workflow or toolPurpose
    python-ci.ymlruff lint · mypy · pytest · coverage gate → Codecov
    go-ci.ymlgolangci-lint · govulncheck · tests · coverage gate → Codecov
    tools/scorecard-scanValidates Scorecard results and writes SARIF; the calling workflow handles upload
    auto-approve-reusable.ymlMetadata-only approval for eligible pull requests under the configured author and reviewer policy

    Consuming a toolkit workflow — always pinned to a full commit SHA:

    jobs:
  test:
    uses: victron-venus/venus-os-ci-toolkit/.github/workflows/python-ci.yml@875762362bb31b4899bf02fdf9e835188dc5eb80

    Non-negotiable rules

    • Pin everything. Every uses: in every workflow resolves to a full commit SHA — never a tag or branch. Tags move; SHAs don't. This is the supply-chain boundary.
    • Harden runners. Workflows include step-security/harden-runner to audit egress network calls.
    • Never push to the default branch. Feature branch from the default branch, open a PR, let CI and CodeQL pass, merge via review. Eligible, non-draft PRs receive auto-approval independently of labels. The automerge label enables automatic merging after required checks and review requirements are satisfied.
    • Conventional Commits. feat:, fix:, docs:, chore: — release tooling parses them.
    • Approval and merge are separate. Follow the approval caller example and merge policy guide. Keep approval jobs metadata-only and preserve the documented eligibility checks.

    Releases

    Application repositories use their .release-policy.json, RELEASING.md and docs/release-workflow.md to define checks, artifacts and release channels. The release pipeline creates immutable beta and RC candidates. Stable promotion requires approval and copies the verified, tested RC bytes without rebuilding. A GitHub release does not deploy production; container registry publication and deployment are separate operations.

    Use the target repository's release commands. Do not create release tags by hand or restore the retired direct-tag publication workflow. Infrastructure and community repositories run validation and explicit deployment instead of application release channels. See the organization release overview.

    Version synchronization

    Review base-version changes through a pull request. The target repository's release policy declares which version files must agree; projects do not all use the same file names or package format. Release tooling allocates candidate versions, applies declared build-time version overlays and records the source revision and artifact checksums. Follow that repository's versioning guide rather than manually changing a version and pushing a tag.

    Why so strict? These repos control physical hardware. A moved tag or an unreviewed workflow edit is not a cosmetic risk — treat CI config with the same care as control code.

    05 · Contributing

    Making your first change

    Start with the target repository's contribution guide. Keep each pull request focused so reviewers can assess its behavior and validation.

    The flow

    1. Fork the target repository — or branch within the org if you're a maintainer.
    2. Create a feature branch from the target repository's default branch. One concern per branch.
    3. Make the change with tests where applicable. Bug fixes come with a regression test.
    4. Commit with Conventional Commits: feat:, fix:, docs:, chore:, refactor:, test:.
    5. Open a pull request. Describe what changes and why; link issues. CI and CodeQL must pass before merge.
    6. Address review feedback. Signed commits may be required on protected branches.

    Local checks before pushing

    Read the target repository's CONTRIBUTING.md and use its documented local validation command. Toolchains, lint rules and test package names differ between projects. If a repository provides scripts/ci.sh, inspect that script and install its documented prerequisites before running it:

    bash scripts/ci.sh

    Where the contribution guide also requires pre-commit, run the checked-in configuration and review any automatic changes:

    python3 -m pre_commit run --all-files

    Report the exact checks run and any limitations in the pull request. Offline checks do not establish physical-device behavior; installation and hardware acceptance are separate steps. See the website contribution guide for this site's own validation requirements.

    Approval gates for control code

    Changes touching the write path — anything that ends up commanding an inverter or battery — get extra scrutiny by design:

    • New setpoints or policy rules must preserve the deployed controller's source-validity, limit and watchdog checks and verify D-Bus write acknowledgements. The archived governance project is not an installed gate.
    • Document the command's actual logging and verification path. Do not claim mandatory event-log coverage when that service is not deployed.
    • Default-off. Risky behavior ships disabled until configuration explicitly enables it.

    Where to ask

    • Bug or feature? Open an issue on the repo using the issue templates — they route to the right maintainers.
    • Questions about Venus OS integration patterns start in integration-patterns discussions or the Victron community forum.
